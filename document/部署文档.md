# 生产部署与数据库迁移手册

线上数据一律按“必须保留”处理。现有服务器的第一次迁移接管与后续发布是两种流程，不要把 baseline 登记放进日常发布脚本。

## 架构

```text
浏览器 -> Nginx :80/:443 -> Next.js standalone :3000 -> MySQL :3306
                                  ^
                         GET /api/health

一次性 migrate 容器 -> prisma migrate deploy -> 可选管理员引导 -> 退出
```

- `db`：默认 `mysql:8.0.46`，数据写入命名卷 `db_data`，不映射公网端口。
- `migrate`：只拿业务数据库账号，执行已提交迁移；可按临时变量创建一个管理员。
- `app`：非 root 运行，不获得 MySQL root 口令；健康检查同时验证应用和数据库。
- `nginx`：仅在 App healthy 后启动并接收流量。

生产暂时锁定 8.0.46 是为了避免普通应用发布触发数据库大版本升级。MySQL 8.4 升级必须单独安排备份、升级检查和恢复演练。

## 新建空环境

服务器需安装 Docker Engine 24+ 和 Docker Compose v2。复制模板并填写强口令：

```bash
cp .env.production.example .env.production
openssl rand -hex 24
openssl rand -base64 32
```

`.env.production` 至少应包含：

```dotenv
MYSQL_IMAGE=mysql:8.0.46
MYSQL_ROOT_PASSWORD=<随机 root 口令>
MYSQL_DATABASE=exam_system
MYSQL_USER=exam
MYSQL_PASSWORD=<随机业务账号口令，建议仅使用字母数字>
AUTH_SECRET=<openssl rand -base64 32 的结果>
AUTH_URL=https://tk.wxlysm.com.cn
```

如空库需要首个管理员，在第一次启动前临时增加：

```dotenv
BOOTSTRAP_ADMIN_USERNAME=<管理员用户名>
BOOTSTRAP_ADMIN_NAME=<管理员姓名>
BOOTSTRAP_ADMIN_PASSWORD=<至少 12 位的一次性强密码>
```

启动：

```bash
docker compose --env-file .env.production up -d --build
docker compose --env-file .env.production ps
docker compose --env-file .env.production logs migrate
docker compose --env-file .env.production logs app
```

如果 Docker Hub 在当前网络下反复超时，可仅在构建时覆盖 Node 基础镜像，不改变运行时架构：

```bash
docker compose --env-file .env.production build \
  --build-arg NODE_IMAGE=m.daocloud.io/docker.io/library/node:22-slim
docker compose --env-file .env.production up -d
```

默认仍为官方 `node:22-slim`；镜像代理只应来自可信的镜像服务，并在发布前核对 image digest。

创建成功后从 `.env.production` 删除三项 `BOOTSTRAP_ADMIN_*`，再运行一次 `up -d` 让 migrate 服务配置被重建。脚本不会覆盖已存在账号的密码。

验证：

```bash
curl --fail https://tk.wxlysm.com.cn/api/health
docker compose --env-file .env.production run --rm migrate \
  node node_modules/prisma/build/index.js migrate status
```

## 已有生产库首次接入迁移历史

这是高风险步骤，不能与普通发布合并盲目执行。第一份 baseline SQL 会创建全部表；若直接对已有库执行会失败。

### 1. 先检查和备份

记录当前部署提交、MySQL 版本、表结构和迁移表是否存在：

```bash
docker compose --env-file .env.production exec db mysql -uroot -p -e \
  "SELECT VERSION(); USE exam_system; SHOW TABLES; SHOW CREATE TABLE Exam; SELECT * FROM _prisma_migrations;"
```

如果 `_prisma_migrations` 不存在，最后一条查询报错是预期信息。然后导出完整 SQL，并把副本保存到另一台机器或对象存储：

```bash
mkdir -p backup
docker compose --env-file .env.production exec -T db sh -c \
  'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers --default-character-set=utf8mb4 "$MYSQL_DATABASE"' \
  > backup/exam_system_before_migrations.sql
```

必须实际做一次“恢复到临时 MySQL 并能启动应用”的演练，才算备份可用。

### 2. 核对 baseline

`20260702000000_initial_baseline` 精确对应提交 `0d0879b` 的 Prisma schema，不含 `Exam.blueprint`。将线上结构与该迁移逐表比对：字段、索引、外键、字符集均一致后，才允许标记为已应用。

如果线上已经有 `Exam.blueprint`、存在额外手工字段，或结构不完全一致，应停止并先生成结构差异方案，不能强行 baseline。

### 3. 标记并应用增量

确认线上等价于 baseline 且数据备份已验证后：

```bash
docker compose --env-file .env.production run --rm migrate \
  node node_modules/prisma/build/index.js migrate resolve \
  --applied 20260702000000_initial_baseline

docker compose --env-file .env.production run --rm migrate \
  node node_modules/prisma/build/index.js migrate deploy
```

第二条命令只应应用 `20260703081020_exam_compose_blueprint`，为 `Exam` 添加 nullable JSON 列，不改现有行。随后再次执行 `migrate status` 并检查应用健康。

## 现有服务器的首次接管

服务器原目录 `/home/tk/wxlysm_exam_sys` 没有 Git 历史，MySQL 8.0.46 使用 `wxlysm-exam-sys_db_data` 卷。旧 `_prisma_migrations` 中有 `20260629073933_init` 与 `20260630120000_class_teaching_sharing`；新版 baseline 在验证结构后才可登记。

1. 将发布提交合并、推送到 `main`，打标签并推送标签。本地执行 `bash scripts/deploy.sh --stage <标签>`，将确切提交上传到 `/home/tk/wxlysm_exam_deploy/releases/<SHA>` 并构建镜像；此时旧应用继续服务。
2. 在维护窗口检查最近两分钟的作答保存活动。首次运行 `release-server.sh bootstrap-nginx <SHA>` 安装维护入口，再运行 `maintenance-on <SHA>`。确认浏览器看到 HTTP 503 维护页，等候现有请求结束。
3. 使用 `release-server.sh backup <SHA> <UTC时间戳>` 导出生产数据库，将 `.sql.gz` 复制到本地 `backup/`，验证 gzip 完整性，并在独立的 MySQL 8.0.46 容器中恢复、核对业务表行数。备份不得只留在生产数据卷内。
4. 使用 Prisma `migrate diff --from-url ... --to-schema-datamodel ... --exit-code` 将线上实际结构与提交 `0d0879b` 的 schema 比对。只有完整匹配时，运行 `migrate resolve --applied 20260702000000_initial_baseline`。旧迁移记录保留，不删除或改写。
5. 再运行 `bash scripts/deploy.sh <标签>`。脚本会重新检查作答活动和迁移白名单，刷新发布前备份，再执行增量迁移、切换 App、核对关键业务表行数与健康检查，通过后自动关闭维护页。人工检查教师和学生登录、组卷、作答与成绩页面。

## 日常发布

本机执行 `bash scripts/deploy.sh <标签或完整提交 SHA>`。发布提交必须位于已推送的 `main`，本机工作区必须干净。脚本通过 SSH 上传该提交的源码，服务器先构建版本化 App/migrate 镜像，不依赖服务器访问 GitHub。密码仅在交互式 SSH 和 `sudo` 提示时输入。

脚本仅自动放行明确识别的 nullable 新增字段迁移；删除、改名、数据改写及未知 SQL 会停止在维护之前。检测到最近作答保存活动时也会停止。进入维护后，会生成本机 `backup/` 中的压缩 SQL 备份，保留最近三份。`backup/` 已被 `.gitignore` 忽略。

构建或预检失败时旧应用继续服务。进入维护后的任何失败都保留维护页；查看迁移和应用日志、确认 schema 兼容性后，再使用旧版本镜像恢复 App。数据库不会自动恢复。日常发布只更新 `app`，不执行整栈 `up`，不重建或升级 `db`。MySQL 镜像升级另立维护任务。

## 停止、备份与恢复

```bash
# 停止并删除容器和网络，但保留数据卷
docker compose --env-file .env.production down

# 重新启动
docker compose --env-file .env.production up -d
```

禁止在生产执行 `docker compose down -v`。恢复应先在独立临时环境演练，再安排停机窗口；不要把未验证的 SQL 直接导入线上卷。

## MySQL 8.0 到 8.4 的独立升级

应用稳定上线后再单独安排：

1. 确认实际 8.0 小版本并升级到支持的最新 8.0 路径节点。
2. 导出并异地保存 SQL，同时保存卷快照。
3. 在临时 MySQL 8.4 中恢复备份，运行官方升级检查。
4. 执行登录、题库创建、组卷、作答、提交、成绩查看全流程。
5. 验证字符集、JSON 字段、外键、迁移状态和性能。
6. 只有恢复与回退演练成功后，才在维护窗口把 `MYSQL_IMAGE` 改为已验证的 8.4 精确版本。

不要直接对唯一的生产卷原地尝试大版本升级。

## 安全与验收清单

- [ ] `.env.production` 未提交，所有口令与开发环境不同。
- [ ] App/migrate 环境中没有 `MYSQL_ROOT_PASSWORD`。
- [ ] `AUTH_URL=https://tk.wxlysm.com.cn`，`AUTH_SECRET` 为随机值。
- [ ] `BOOTSTRAP_ADMIN_*` 创建成功后已移除。
- [ ] 防火墙只开放 80/443，数据库无公网映射。
- [ ] SQL 备份已异地保存并完成恢复演练。
- [ ] `db` 与 `app` 显示 healthy，`migrate` 退出码为 0。
- [ ] `/api/health` 返回 200，失败响应不泄露数据库信息。
- [ ] 管理员、教师、学生登录及核心业务流程均已验证。
- [ ] 未执行 `migrate reset`、`db push`、`down -v` 或未演练的大版本升级。
